# Cutscene Guide

How the cinematic system is meant to work, and the rules a cutscene must obey.

**Status: not implemented.** No cutscene system exists yet. This document is the
contract that `CutsceneDirector` will be built against, written now so the design
is fixed before implementation starts forcing decisions on it. See
`docs/ACCEPTANCE.md` M10 for the criteria it has to satisfy.

Nothing in this document is a stub or a placeholder — it is a specification. The
first milestone that touches cutscenes implements it; before that, there is
genuinely nothing here.

---

## 1. Principles

**Cutscenes are data, not code.** A cutscene is a `.tres` resource holding an
ordered list of events. Authoring a cutscene means writing a resource, not
writing a script, and certainly not adding an `if` to `main.gd`.

**The player must never become permanently stuck because a cutscene was
interrupted.** This is the single hardest requirement in the system. Every
invocation takes a snapshot of the state it is about to change, and restoration
does not depend on the cutscene having run to completion.

**Interruptions are not errors.** Skipping, pausing, saving, quitting, scene
changes, and death are all normal. A cutscene that assumes it will finish is
broken by construction.

**A cutscene never permanently owns the player.** It locks input while it plays
and releases it when it stops — including when it stops because of an error.

---

## 2. Layout

```
scripts/cutscenes/
    cutscene_director.gd     # plays a cutscene, owns the lock
    cutscene_player.gd       # Resource: ordered events
    cutscene_event.gd        # Resource: one step, with a `step()` method
    cutscene_context.gd      # snapshot of everything a cutscene can touch
    cutscene_camera.gd       # camera cut/move/shake, restores on stop
    events/                  # one script per event type

scenes/cutscenes/
    intro.tres               # data
    first_village.tres       # data
```

Per `AGENTS.md` rule 1, any `.tscn` needed here is generated by a script in
`tools/`, not hand-placed.

## 3. The event vocabulary

Every event is a `Resource` subclass implementing `step(ctx: CutsceneContext)`.
It either completes immediately or awaits a signal/timer, and it always
registers its undo with the context.

| Category | Events |
|---|---|
| Timing | `wait` |
| Actors | `move_actor`, `rotate_actor`, `look_at`, `spawn`, `despawn`, `teleport_player`, `set_actor_visibility` |
| Camera | `camera_move`, `camera_cut`, `camera_shake`, `look_at_target` |
| Presentation | `fade`, `letterbox`, `play_animation`, `play_particles`, `set_environment`, `play_sound`, `play_music` |
| Dialogue | `dialogue` (speaker, portrait, text, choices) |
| Logic | `set_flag`, `branch`, `give_item`, `start_quest`, `complete_quest`, `unlock_area`, `play_cutscene` |
| State | `set_time`, `wait_for_player_input` |

`branch` takes a flag condition and two sub-lists. `play_cutscene` nests, so a
cutscene is composable rather than a monolith.

## 4. Save-safety

This is the part that is easy to get wrong, so the rules are explicit.

### Snapshot before mutating

`CutsceneContext` records the previous value of everything a cutscene changes,
before changing it:

- camera transform, projection and FOV
- player input lock state, velocity and visibility
- each NPC's transform, animation state and schedule override
- the game's time/pause state
- any gameplay flag the cutscene sets

### Restoration is unconditional

Restoration runs from `_exit_tree` / the `finished` / `skipped` signal — not at
the end of the event list. If a cutscene errors halfway, restoration still runs.
The context is the source of truth about what to undo, not the cutscene's
progress.

### Skipping is a completion with a shortcut

`skip` stops playback and then runs the same restoration path as natural
completion, plus a **catch-up** phase that applies the flags and rewards of any
skipped events that must still take effect.

Without catch-up, skipping the village introduction means the village-introduced
flag never gets set, and the gate that depends on it can never open. With naive
catch-up, skipping means the player receives the reward but not the item they
were supposed to have picked up. So each event declares its skip behaviour
explicitly:

| Mode | Meaning |
|---|---|
| `SKIP_APPLY` | run the effect anyway (flags, rewards, quests) — the default |
| `SKIP_SKIP` | do not run it (a sound, a camera flourish) |
| `SKIP_REQUIRED` | cannot be skipped at all; the game waits |

A `SKIP_REQUIRED` event is how a death or a game-over beat stays uncancellable
without special-casing it everywhere.

### No duplicate rewards

Catch-up runs exactly once, guarded by the event index reached rather than by the
skip path, so a cutscene cannot be skipped, replayed by a scene reload, and paid
twice.

## 5. Locking

The director owns a single `player_lock` flag. Taking it stores:

- input lock state
- velocity, so the player does not slide when control returns
- visibility, for cuts that hide the body
- any active interaction the player was mid-way through

Releasing restores all of it. The lock is re-entrant-safe: a nested cutscene
saves the outer lock state rather than assuming there was none.

While locked: no movement, no camera look, no interaction, no pause menu.
`pause` is also suspended — the cutscene clock is not game time, and game time
does not advance during a cutscene unless the cutscene explicitly advances it.

## 6. Interruption matrix

Every row must restore cleanly. Each of these needs a test.

| Interruption | Expected behaviour |
|---|---|
| Player skips | Restoration + catch-up, back to play |
| Player pauses | Cutscene clock stops; game time already stopped |
| Player quits mid-cutscene | Save-safe state; no half-applied flags |
| Scene reload mid-cutscene | Context discarded cleanly; no dangling locks |
| Player dies mid-cutscene | Cutscene aborted; restoration runs; death proceeds |
| Event errors | Restoration still runs; error surfaces, not swallowed |
| Game window unfocused | Cutscene pauses rather than advancing unattended |
| Re-entrant cutscene | Outer state saved and restored by the inner |

## 7. Required cutscenes

From the design brief. Each is a milestone deliverable, not a nice-to-have:

1. New game introduction
2. Arrival at the farm
3. First village introduction
4. First major NPC event
5. First mine discovery
6. First boss encounter
7. Major seasonal story scenes
8. Relationship heart scenes
9. Romance scenes
10. Marriage ceremony
11. Major restoration/progression scenes
12. Final story sequence
13. Ending and credits

Every major story beat gets cinematic presentation. A story beat delivered as a
dialogue box with a static camera is a stub, and stubs are forbidden.

## 8. Testing

`tests/suites/test_cutscenes.gd` must cover:

- each event type executes without error
- skip restores camera, input, time and NPC state
- skip applies `SKIP_APPLY` effects and omits `SKIP_SKIP` effects
- a `SKIP_REQUIRED` event resists skipping
- aborting mid-cutscene restores state exactly
- replaying a cutscene after a skip does not duplicate rewards
- the player is never left locked, under any interruption in the matrix above

The restoration tests are the point of the suite. "The cutscene played" is easy;
"the player is still playable afterwards" is the actual requirement.

---

## 9. Authoring a cutscene

Write a `.tres` listing events in order. Keep it declarative — if authoring a
scene requires a script, the event vocabulary is missing something, and that is a
bug in the system rather than in the scene.

Keep cutscenes short and skippable. A cutscene that outstays its welcome is a
usability defect even when it restores perfectly.
