# Decisions

Engineering and creative decisions, with the reasoning that produced them. One
entry per decision that a future reader would otherwise second-guess.

Append newest-last. Cite what forced the decision, not just what it was.

---

## D1 — Godot 4.5, GDScript, no addons, no C#

**Status:** settled

The project had a Unity 6 C# implementation and a TypeScript/Vite web build. Both
are gone. Unity is uninstalled; the license backup at
`C:\Users\mohan\unity-licensebackup` is retained.

Godot's `Node`/`Resource` types are the entire framework. No addon provides
anything we need that we would rather own. GDScript's reference semantics and
signal model fit the component approach better than C#'s would have, and
shipping a single headless-verifiable binary is worth more than language
ecosystem breadth.

**Consequence:** techniques needed from the old build get ported to GDScript
*with a test*, not reintroduced as C#. `docs/SALVAGED_DESIGN.md` exists so that
the recovered edge cases are not lost in the port.

---

## D2 — Scenes are generated by scripts, never hand-placed

**Status:** settled

There are no `.tscn` files to edit by hand. Each is written by a generator under
`tools/` and run headlessly.

A headless box has no editor and no human at the keyboard. "Drag a node into the
scene" is a task that cannot be completed or verified on CI, and leaving a note
asking a human to finish it means it never gets finished. Generating scenes makes
the result reproducible and reviewable as a diff.

`AGENTS.md` rule 1 states this as a hard constraint: if a task cannot be
expressed as a script that writes the `.tscn`, restructure the task.

## D3 — `EventBus` is the only cross-system channel

**Status:** settled

27 signals, and no system holds a reference to another system and calls into it.

The alternative — farming asking time what day it is — looks harmless for two
systems and becomes a mesh at six. Time needs to know crops were planted, the HUD
needs to know both, economy needs to know the day ended. A hub keeps that a star
graph.

The cost is that signals are strings and go unchecked at compile time. That cost
is paid deliberately: `EventBus` is one small file nobody edits casually, and a
central hub is inspectable in a way a mesh of references is not.

**Consequence:** signals for systems that do not exist yet are declared now, so
the contract is fixed before the first implementation forces a choice. Adding a
signal later is cheap; renaming one after five systems depend on it is not.

## D4 — Visual mesh and collider share one source of truth

**Status:** settled — forced by a real bug

`WorldBuilder.terrain_height(x, z)` is a pure, deterministic function. The
`ArrayMesh` and the `ConcavePolygonShape3D` are both generated from one vertex
buffer in one pass.

This was not a preference. The original ground was a flat visual plane *and* a
flat box collider, authored independently. The pond water at `y=-0.8` therefore
rendered underneath opaque grass at `y=0`, and the player walked on solid ground
straight over the water. Every functional test passed; a headless run cannot see
that water is invisible.

Nothing in the codebase represented a depression, so nothing could disagree about
one. Deriving both from one function makes the class of bug unrepresentable
rather than merely fixed.

**Consequence:** the general rule is that anything the player can stand on has
its collision derived from the same values as its mesh, in the same function.

### D4a — Collision winding is reversed relative to the render winding

`ConcavePolygonShape3D` treats a clockwise face (viewed from above) as its front;
the renderer's front face is counter-clockwise. The collision face list is
expanded in reverse.

Feeding the render winding straight through produces a mesh that looks perfect
and collides with nothing — rays pass through, the player falls. Reverse the
whole thing instead and the mesh renders inside out. So the reversal goes on the
collider side only, and the comment in `world_builder.gd` says why.

### D4b — `set_faces()`, never `data`, for a ConcavePolygonShape3D

`data` looks like the obvious assignment and is wrong: it reinterprets a flat
`PackedVector3Array` as consecutive face triples. A 3875-vertex grid silently
becomes 1291 arbitrary triangles plus two leftover vertices. No error, no
warning, no collision.

Found by probe rather than by reading docs, because the docs do not state it
plainly. Both facts above were confirmed with a throwaway script that built a
known flat quad and raycasted downward: `data =` misses, `set_faces()` hits at
`y=0`. The script was deleted after the fix; the reasoning lives in the code
comment and here.

## D5 — `InputActions` is a `class_name`, not an autoload

**Status:** settled

It is a bag of `StringName` constants with no state and nothing to own. An
autoload would instantiate a node that never enters the tree and never does
anything.

Keeping it a `class_name` also means the action-name registry is available to
`--script` tool runs without the autoload-identifier trap described in
`AGENTS.md`.

---

## D6 — Interaction discovery is pull-based, with no central registry

**Status:** settled

`Interactable.resolve(collider)` walks up from the hit collider and checks each
ancestor's children. No global list of interactables exists.

A registry would need central list syncing across `free()` and reparent, and it
inverts the dependency: props would have to know a player exists. Pull-based
resolution handles both `body > Interactable` and
`prop > body > Interactable` layouts with no bookkeeping at all.

---

## D7 — Interaction colliders are padded to a minimum height

**Status:** settled

Any prop the player can interact with gets a collider at least 2.4m tall.

The crosshair sits at roughly 1.62m. A genuinely short prop — a 0.9m crate —
would otherwise sit below the crosshair and be impossible to aim at. Padding the
collider rather than raising the crosshair keeps the aiming model uniform and
does not distort the player's view.

This is a real gameplay bug found in Group 3, not a hypothetical.

---

## D8 — Only the orchestrator commits

**Status:** settled

Workers never run `git commit`, `reset`, `stash` or `checkout`. A worker that can
commit will eventually commit a half-finished group that does not boot.

Shared-tree editing is restricted to the lane in `AGENTS.md`. A worker that needs
another lane changed reports it instead.

---

## D9 — The pond regression test raycasts; it does not read node positions

**Status:** settled

`tests/suites/test_world_geometry.gd` measures terrain height by raycasting the
real collider.

The first version of this suite compared `Pond.position.y` to
`GroundMesh.position.y`. Both are node transforms, and after the fix both nodes
sit at the origin while the ground *surface* dips into the basin — so the
assertion was measuring the wrong thing and would have passed on broken geometry.

A raycast is what "where does the player stand" actually means. Asserting through
the same interface the game uses is the difference between a test that describes
the world and one that describes the implementation.

The same reasoning applies to the "valley floor is flat" check: it asserts a
relationship between two sampled points, so re-tuning the valley's dimensions
does not invalidate it.

---

## D10 — A failing test is evidence, not an obstacle

**Status:** settled

Do not weaken assertions to make a suite pass. When something fails, establish
whether the code or the test is wrong, and record which it was.

During the Group 4B fix, four unrelated tests failed
(`player_does_not_sink_into_terrain`, `ground_supports_the_spawn_point`,
`world_has_ground_surface`, and the interaction suite) while the collider was
broken. The tests were right. The temptation to adjust their expectations to
match a broken collider is exactly how the original pond bug survived three
groups of green tests.

Equally, a test that asserts the wrong thing gets fixed — and the fix is
recorded, as with D9.

---

## D11 — Logs are structured and routed through `Log`

**Status:** settled

No `print()` in gameplay code. Every line goes through the `Log` autoload with a
level, so verbose output can be toggled in a shipped build and the boot check can
assert on specific messages.

This is why the boot check can verify `game_ready` fired and the phase reached
`PLAYING` rather than merely "the process exited zero" — which, as
`DEVELOPMENT_STATUS.md` records, was a false positive until it was tightened.

---

## D12 — `check.ps1` is the only supported validation

**Status:** settled

Three stages, each under a hard timeout, non-zero on any failure: `import`,
`tests`, `boot`. Zero `SCRIPT ERROR` lines in stderr is part of passing.

"Tests exist" is not verification. A stage that exits 0 while logging a compile
error is a broken stage — which is precisely the failure mode that let
`boot_check.gd` pass on a scene that did nothing.

The script kills orphaned Godot processes on exit, so a broken run cannot leave the
machine stuck.

## D13 — The day rolls at the 2:00 AM collapse, not at midnight

**Status:** settled — overrides a rule in `docs/SALVAGED_DESIGN.md`

`docs/SALVAGED_DESIGN.md` says "advancing at midnight rolls the day." That rule
is not implemented as written, and the divergence is deliberate.

The clock runs 6:00 AM → 2:00 AM. Midnight sits 18 hours into that window, in the
middle of an ordinary evening session. Rolling the calendar there means a
rollover with no gameplay event to justify it, and it puts the boundary two
hours *before* the point where the player is actually forced to stop. The 2:00 AM
collapse is the last instant a player can occupy, so it is the only honest place
to end a day.

The salvaged rule also contradicts the salvaged edge-case list, which says both
"at 2:00 AM the farmer collapses *and* the day rolls" and "advancing at midnight
rolls the day." Both cannot be the boundary. Since the collapse is the enforced
end of play, it wins.

**Consequence:** `to_absolute_minutes` is unchanged and still offsets pre-dawn
times by `+ 1080`, so 0:00–5:59 AM remains the *tail* of the current day. Only
the rollover trigger moved. `Clock.advance` rolls at `PASS_OUT_ABSOLUTE`, and
`tests/suites/test_time.gd::advancing_past_midnight_does_not_roll_the_day` pins
the corrected behaviour.

### D13a — `to_game_minutes` is HHMM, not minutes

`docs/SALVAGED_DESIGN.md` calls it "schedule-friendly minutes" with 6:00 AM = 600,
midnight = 2400, 2:00 AM = 2600. Those are HHMM values, not elapsed minutes —
there is no scale where midnight is 2400 and 2:00 AM is 2600 minutes.

So it is implemented as `hour * 100 + minute` with hours below 6 shifted past 24.
The name is kept because the salvaged notes and the not-yet-written NPC schedule
data both use it, and the docstring says plainly that the unit is HHMM.

Monotonicity is scoped to *one day walked chronologically*, 6:00 AM onward. A
naive 24-hour sweep asserts 5:59 AM → 6:00 AM is increasing, which it is not
(2950 → 600) — that transition is the start of the next day, not a step
backwards. The first version of the test swept 0:00 → 23:59 and failed at 6:00
for exactly that reason; the test was wrong, not the scale.

### D13b — Sleeping rolls the day; collapsing does not

`Clock.advance` already rolls the calendar at the collapse point. So waking from
a collapse must **not** roll again, or the player loses a day for having passed
out — the penalty would be doubled.

- `Clock.next_day_morning` — sleep. Always rolls, whatever hour you go to bed at.
  A 1:00 AM sleep lands on the following morning, because that day's 6:00 AM has
  already gone by.
- `Clock.wake_after_collapse` — carried home. Does not roll. Just clears
  `passed_out` and lands on 6:00 AM of the current date.

Before this split there was a single `next_day_morning` doing both jobs, and
`TimeService.sleep_until_morning` computed `var rolled := time.day_of_month > 0`
— always true, and the day it emitted was the *new* one, not the day that
finished. Three bugs, one tautology. The tests
`next_day_morning_works_from_a_late_night_clock` and
`sleeping_rolls_the_day_but_collapsing_does_not` now pin the split.

### D13c — The clock freezes at 2:00 AM

`TimeService.advance_tick` is a no-op while `passed_out` is set. Without this the
calendar spins through empty days while the game waits for the player to
acknowledge passing out — a 10-minute day becomes hundreds of days of nothing.
The end of the day is `sleep_until_morning` or `wake_after_collapse`, never
another tick.

### D13d — A corrupt save degrades field by field, it is not rejected whole

`WorldTime.from_dict` clamps each field independently instead of discarding the
payload when any field is missing or out of range. Rejecting the whole save
loses a year of progress over one corrupt int, which is a far worse failure than
losing one field.

The practical reason this matters here: `posmod` and `clamp` disagree on
negatives. A `season` of `-1` read with a modulo wrap lands on index 3 — Winter —
and every `season_name` array lookup is then one short. Negative values clamp to
0. `negative_values_are_clamped_not_wrapped` pins it.
